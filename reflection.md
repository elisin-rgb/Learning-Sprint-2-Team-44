# Reflection

Building the Buffer Overflow Visualizer helped me understand the topic more clearly because I had to turn an abstract description of memory corruption into something a learner could see and interact with. Before building the visualization, I understood that a buffer overflow happens when a program writes more data than a buffer can hold. While working on the project, I had to think more specifically about what the extra bytes would overwrite and why the saved frame pointer and return-address area are important parts of a simplified stack-frame model.

My workflow was AI-assisted. I first chose buffer overflow instead of integer overflow or the Trusting Trust topic because a stack-frame visualization could make the concept easy to understand without creating a real exploit. I then planned a simple static website with an 8-byte buffer and several neighboring memory regions. I used AI to help generate the initial HTML, CSS, JavaScript, README, and explanation of the concept. After that, I reviewed the generated code and adjusted the design so the application had meaningful interaction rather than just displaying a static diagram.

The main interaction I added was a text input that places one character into each simulated byte of memory. The application also has a button to fill the visualization, a reset button, and a slider that lets the user reveal the bytes gradually. When the input is longer than eight bytes, the application clearly reports that an overflow has occurred and shows the additional characters entering neighboring simulated stack memory. This made the relationship between input size and memory boundaries much easier to visualize.

One important thing I learned was that a visualization like this must distinguish between a teaching model and a real computer's memory layout. Real stack frames depend on the architecture, compiler, optimization settings, calling convention, and other factors. Therefore, I intentionally labeled the frame pointer and return address as simulated areas rather than presenting the diagram as an exact representation of every real program.

I also learned that AI-generated code still needs to be reviewed and tested. I checked the input behavior, reset behavior, slider behavior, and the overflow message instead of assuming the first generated version was correct. I also made sure the project did not become an exploit or attack tool. The final application demonstrates the security concept without generating shellcode, manipulating real memory, or providing exploit instructions.

Overall, this project deepened my understanding because I had to connect the conceptual definition of a buffer overflow with a concrete memory model and an interactive user experience. The biggest takeaway is that a buffer has a fixed boundary, and failing to enforce that boundary can cause data intended for one memory region to overwrite other data.
